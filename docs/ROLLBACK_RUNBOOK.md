# Deployment Rollback Runbook

## Overview
This runbook outlines the process for rolling back a MedTrace AI staging or production deployment in the event of an application failure, configuration error, or data anomaly. 

## Rollback Scenarios

### 1. Stateless Application Failure (Code Bug / Configuration Error)
*Condition:* The newly deployed `medtrace_backend` or `medtrace_frontend` images are failing, but database migrations (if any) are backward compatible.

**Procedure:**
1. Identify the previous known-good image tags.
2. Update `docker-compose.yml` or your orchestration manifests to point to the stable image tags.
3. Restart the application containers:
   ```bash
   docker-compose up -d medtrace_backend medtrace_frontend
   ```
4. Verify health endpoints return `200 OK`.

### 2. State-Incompatible Failure (Destructive Migrations)
*Condition:* The deployment included a database migration (`alembic upgrade head`) that altered schema structures (e.g., dropped a column) in a way that breaks the old application code.
*Warning:* Alembic downgrades (`alembic downgrade -1`) can result in data loss if they drop newly populated columns.

**Procedure:**
1. **Evaluate Data Loss:** Determine if the rollback will destroy new clinical data written since the migration.
2. **Execute Downgrade:** If safe, downgrade the schema *before* reverting the application code:
   ```bash
   docker exec medtrace_backend alembic downgrade -1
   ```
3. Revert the application images to the known-good version and restart:
   ```bash
   docker-compose up -d medtrace_backend medtrace_frontend
   ```

### 3. Total Disaster (Database Corruption / Critical Outage)
*Condition:* The database is structurally corrupted, or an active attacker has compromised the environment.

**Procedure:**
1. Terminate all application ingress by stopping the containers:
   ```bash
   docker-compose stop medtrace_frontend medtrace_backend
   ```
2. Isolate the database volume for forensic analysis.
3. Deploy a fresh Postgres container and execute the Restore Procedure (see `STAGING_DEPLOYMENT_RUNBOOK.md`) using the most recent pre-deployment backup.
4. Restart the stable application images.

## Limitations & Architectural Constraints
- **Migration Backward Compatibility:** Migrations in MedTrace AI are *not guaranteed* to be backward compatible. A column rename will instantly break the previous application version. Always evaluate `alembic downgrade` logic carefully.
- **Audit Trail Immutability:** Downgrading the database will NOT delete `AuditEvent` rows generated by the failed application version, preserving the forensic trail of the failed deployment.
